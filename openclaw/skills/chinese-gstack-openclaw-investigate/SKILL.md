# 系统化调试

## 铁律

**没有根因调查,就不要动手修复。**

修症状只会变成打地鼠式调试。每一次没有解决根因的修复,都会让下一个 bug 更难找。先找到根因,然后再修。

---

## 阶段 1:根因调查

在形成任何假设之前,先收集上下文。

1. **收集症状:** 阅读错误消息、堆栈跟踪、重现步骤。如果用户提供的上下文还不够,一次只问一个问题。不要一次问五个问题。

2. **阅读代码:** 从症状反推到潜在原因,追踪代码路径。搜索所有引用,阅读故障点周围的逻辑。

3. **检查最近改动:**
   ```bash
   git log --oneline -20 -- <affected-files>
   ```
   这之前是工作的吗?改了什么?如果是回归,根因就在 diff 里。

4. **重现:** 你能稳定触发这个 bug 吗?如果不能,在继续之前收集更多证据。

5. **检查 memory** 里同一区域的过往调试 session。同一文件上反复出现的 bug 是架构异味。

输出: "{根因假设: ...}"……一段具体的、可检验的声明,讲清楚哪里出错了、为什么。

---

## 阶段 2:模式分析

检查该 bug 是否匹配已知模式:

**Race condition(竞态条件)**……间歇性的、时序敏感的。查看对共享状态的并发访问。

**Nil / null 传播**……NoMethodError, TypeError。可选值上缺少守卫。

**State corruption(状态损坏)**……数据不一致、部分更新。检查事务、回调、钩子。

**Integration failure(集成失败)**……超时,意外的响应。外部 API 调用、服务边界。

**配置漂移**……本地能跑,staging / prod 上挂掉。环境变量、feature flag、数据库状态。

**Stale cache(缓存过期)**……显示的是旧数据,清缓存后正常。Redis、CDN、浏览器缓存。

同时检查:
- 项目里同一相关问题的已知 issue
- 同一区域的过往修复 git log。同一文件上反复出现的 bug 是架构异味,不是巧合。

**外部搜索:** 如果该 bug 与已知模式都不匹配,在网上搜索该错误类型。**先脱敏:** 去掉 host、IP、文件路径、SQL、客户数据。搜索错误类别,而不是原始消息。

---

## 阶段 3:假设检验

在写任何修复之前,验证你的假设。

1. **确认假设:** 在疑似根因处添加临时 log、断言或调试输出。运行重现脚本。证据是否吻合?

2. **如果假设错了:** 搜索该错误(先脱敏敏感数据)。回到阶段 1。收集更多证据。不要瞎猜。

3. **3-strike 规则:** 如果 3 个假设都失败,**停下来。** 告诉用户:

   "3 个假设都测试过了,没有一个匹配。这可能是架构问题,而不是简单的 bug。"

   选项:
   - 带着新假设继续调查(描述它)
   - 升级到人工评审(需要熟悉该系统的人)
   - 加日志然后等待(在该区域埋点,下次再抓)

**红旗**……如果你看到任何一项,放慢:
- "先这样修一下再说"……没有"再说"。要么修对,要么升级。
- 在追踪数据流之前就提议修复……你是在瞎猜。
- 每次修复又揭示出别处的新问题……是层错了,不是代码错了。

---

## 阶段 4:实施

根因一旦被确认:

1. **修根因,而不是症状本身。** 消除真实问题所需的最小改动。

2. **最小 diff:** 最少的文件、最少的行变更。忍住重构相邻代码的冲动。

3. **写一个回归测试**,它:
   - 在没有该修复时 **失败**(证明该测试有意义)
   - 在有该修复时 **通过**(证明该修复有效)

4. **跑完整的测试套件。** 不允许回归。

5. **如果该修复触及超过 5 个文件:** 在继续之前,向用户标记该影响面。这对 bug 修复来说太大了。

---

## 阶段 5:验证与报告

**新鲜验证:** 重现原始的 bug 场景,确认它已被修复。这不是可选项。

运行测试套件。

输出一份结构化的调试报告:

**DEBUG 报告**
- **症状:** 用户观察到什么
- **根因:** 实际哪里出错了
- **修复:** 改了什么,带文件引用
- **证据:** 测试输出、重现脚本显示修复有效
- **回归测试:** 新测试的位置
- **相关:** 同一区域的过往 bug、架构备注
- **状态:** DONE | DONE_WITH_CONCERNS | BLOCKED

把该报告保存到 `memory/`,并打上当天的日期,这样未来的 session 可以引用。

---

## 重要规则

- **3 次以上修复尝试:停下来质疑架构。** 是架构错了,不是假设错了。
- **绝不应用你无法验证的修复。** 如果你无法重现并确认,就不要发布。
- **绝不说"这样应该能修好"。** 验证并证明。跑测试。
- **如果修复触及超过 5 个文件:** 在继续之前向用户标记。
- **完成状态:**
  - DONE……找到根因,应用修复,写了回归测试,所有测试通过
  - DONE_WITH_CONCERNS……修好了但无法完全验证(例如,间歇性 bug,需要 staging)
  - BLOCKED……调查后根因不清楚,已升级
