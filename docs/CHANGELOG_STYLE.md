# CHANGELOG + VERSION 风格

逐字从 CLAUDE.md 移出(减少 token 加载)。在编写任何 `## [X.Y.Z]` CHANGELOG 条目**之前**阅读此内容。

## 版本控制和分支范围的条目

逐字从 CLAUDE.md 移出(#2096 大小限制)。自主版本策略(无需询问选择版本;默认为 PATCH)作为单一来源保留在 CLAUDE.md 中。

**版本控制不变量(工作区感知的发布)。** VERSION 是一个单调有序的发布标识符,而不是严格的 semver 承诺。提升级别(major/minor/patch/micro)在发布时表达意图。在同一提升级别内队列推进超过已声明的版本是明确允许的 — 如果分支 A 声明 v1.7.0.0 作为 MINOR,分支 B 也是 MINOR,则 B 在 v1.8.0.0 处落地(相对于 main 仍然是 MINOR)。下游消费者**不得**依赖"MINOR = 仅功能,PATCH = 仅修复"作为严格合约。这就是为什么 `bin/gstack-next-version` 在所选提升级别内推进,而不是在发生冲突时重新选择级别。

**package.json 携带 npm 有效的翻译,而不是 VERSION 逐字。** VERSION 保持 4 位数的真实来源(例如 `1.67.0.0`);package.json 和任何带有 `version` 字段的子目录清单获得 3 位数的 npm 有效翻译(`1.67.0`),并且 lockfile `version` 字段仅在 lockfile 已存在时同步。`bin/gstack-version-bump`(通过 `lib/version-source.ts`)拥有翻译,并判断翻译形式的漂移 — 不要通过手工"修复"明显的不匹配,也不要将 4 位版本写入 package.json(npm 拒绝)。基本原理和翻译规则存在于 `lib/version-source.ts` 头中;`test/gstack-version-bump.test.ts` 固定合约。

**VERSION 和 CHANGELOG 是分支范围的。** 每个发布的特性分支都会获得自己的版本提升和 CHANGELOG 条目。该条目描述**此**分支添加的内容 — 而不是 main 上已有的内容。

**CHANGELOG 条目是 main 和发布分支之间的差异 — 用户升级时得到的内容。不是分支如何到达那里。** 在该条目上登陆的读者应该了解他们现在可以做以前不能做的事情;他们不应该了解分支的内部版本提升、我们中途捕获并修复的错误、我们运行的计划评审,或者我们压缩的提交。那是分支开发叙述。它属于 PR 描述和提交消息,而不是 CHANGELOG。

**永远不要在 CHANGELOG 条目中引用分支内部版本。** 如果你的分支在开发过程中将 VERSION 从 v1.5.0.0 → v1.5.1.0 → v1.6.0.0 提升,并且只有最终的 v1.6.0.0 发布到 main,则该条目必须读起来好像 v1.5.1.0 从未存在过。具体来说,**永远不要**写:
- "v1.5.1.0 有一个 v1.6.0.0 修复的错误" — 读者不知道 v1.5.1.0;它是分支内部工件。
- "v1.5.1.0 的发布标题坏了,因为..." — 同样的原因。从 main 的角度来看,v1.5.1.0 从未发布。
- "修复前的测试编码了破坏的行为" — 这是贡献者的胜利圈,而不是用户收益。
- "两次外科手术编辑,都在调度路径中" — 补丁的微观叙述。

相反,描述已发布的系统:"浏览器端到端技能运行,具有预期的标签页访问语义。"如果已发布系统的某个属性值得强调(例如,"技能 spawn 获得宽容的标签页访问;pair-agent 隧道 token 需要所有权"),将其记录为属性,而不是修复。已发布的系统是用户得到的;通向该系统的路径对用户不可见。

**何时编写 CHANGELOG 条目:**
- 在 `/ship` 时(步骤 13),不是在开发期间或分支中途。
- 该条目涵盖此分支上的所有提交与基础分支的对比。
- 永远不要将新工作折叠到已发布到 main 的先前版本的现有 CHANGELOG 条目中。如果 main 有 v0.10.0.0 并且你的分支添加了功能,则提升到 v0.10.1.0 并创建一个新条目 — 不要编辑 v0.10.0.0 条目。

**编写前的关键问题:**
1. 我在哪个分支上?**此**分支更改了什么?
2. 基础分支版本是否已发布?(如果是,则提升并创建新条目。)
3. 此分支上是否已经存在涵盖早期工作的现有条目?(如果是,则将其替换为最终版本的统一条目。)

**合并 main 并不意味着采用 main 的版本。** 当你将 origin/main 合并到特性分支时,main 可能会带来新的 CHANGELOG 条目和更高的 VERSION。你的分支仍然需要在上面添加自己的版本提升。如果 main 是 v0.13.8.0 并且你的分支添加了功能,则提升到 v0.13.9.0 并创建一个新条目。永远不要将你的更改塞入已发布到 main 的条目中。你的条目放在最上面,因为你的分支接下来登陆。

**合并 main 后,始终检查:**
- CHANGELOG 是否有你自己的分支条目,与 main 的条目分开?
- VERSION 是否高于 main 的 VERSION?
- 你的条目是否是 CHANGELOG 中最顶部的条目(在 main 最新条目之上)?
如果任何答案是否,请在继续之前修复它。

**在任何移动、添加或删除条目的 CHANGELOG 编辑之后,** 立即运行 `grep "^## \[" CHANGELOG.md` 以验证没有重复且反向时间顺序合理。版本号之间的间隔是可以的。在 v1.5.0.0 处的分支在 main 上没有 v1.5.2.0 或 v1.5.3.0 条目而在 v1.6.4.0 处发布是正确 — 那些是永远未登陆的分支内部版本号。不要用占位符条目回填间隔。

**永远不要孤立分支内部版本。** 如果你的分支在开发过程中多次提升 VERSION(v1.5.1.0 → v1.5.2.0 → v1.6.4.0,假设)并且那些较早的条目从未发布到 main,则最终发布将它们全部合并到最终版本的单个条目中(v1.6.4.0)。折叠它们 — 删除旧条目并将其内容移动到最终条目中,重新设置表列的版本。读者看到一个发布,而不是分支日记。间隔是可以的(v1.6.3.0 → v1.6.4.0 在 main 上没有 v1.5.x 是正确的)。

CHANGELOG.md **是给用户的**,而不是贡献者。像产品发布说明一样编写它:

- 首先介绍用户现在可以**做**的他们以前不能做的事情。推销该功能。
- 使用简单的语言,而不是实现细节。"你现在可以..."而不是"重构了..."
- **永远不要提及 TODOS.md、内部跟踪、评估基础设施或面向贡献者的详细信息。** 这些对用户不可见,对他们毫无意义。
- 将贡献者/内部更改放在底部的单独"For contributors"部分。
- 每个条目都应该让某人想到"哦,不错,我想试试。"
- 没有行话:说"每个问题现在告诉你你在哪个项目和分支上",而不是"通过 preamble resolver 在 skill 模板中标准化 AskUserQuestion 格式"。

**仅记录 main 和此更改之间发布的内容。** 读者不在乎我们是如何到达这里的。始终不要放入 CHANGELOG:
- 分支重新同步、与 main 的合并提交、rebase 活动。
- 计划批准、评审结果(CEO / eng / design / outside-voice / codex findings)、AskUserQuestion 决策、范围协商。
- "工作排队中"、"计划已批准"、"进行中"、"稍后发布" — CHANGELOG 记录的是**已经**发布的内容,而不是**可能**发布的内容。
- 当没有面向用户的工作实际登陆时的版本提升内务处理。

如果基础分支版本和此版本之间的差异没有面向用户的更改(仅合并、仅 CHANGELOG 编辑、仅占位符工作),诚实的条目是一句话:"用于分支提前纪律的版本提升。还没有面向用户的更改。"就此打住。不要填充。不要解释最终将发布的计划。不要叙述分支的历史。当真正的工作登陆时,该条目将在 /ship 时替换此条目。

### 提高支持的最低版本(`capy/support.env`)

发布标记也可以提高 `capy/support.env` 中的 `GSTACK_MIN_REVISION`。每个低于它的 Capy 机器在其下一次会话开始时被快进,因此仅出于安装诚实性或安全修复而提高它,并在标记时将其设置为正在发布的 VERSION。它永远不会超过 VERSION(`test/capy-skill-wrapper.test.ts` 固定这一点)。详细信息:[capy-install.md](capy-install.md#raising-the-supported-minimum)。

## 条目格式

### 发布摘要格式(每个 `## [X.Y.Z]` 条目)

CHANGELOG.md 中的每个版本条目必须以 GStack/Garry 声音的发布摘要部分开始,一个视口的散文 + 表格,落地如判决,而不是营销。项目化的 changelog(子部分、项目符号、文件)放在该摘要**下面**,由 `### Itemized changes` 标题分隔。

发布摘要部分由人类、自动更新智能体以及任何决定是否升级的人阅读。项目化列表适用于需要确切知道更改内容的智能体。

每个 `## [X.Y.Z]` 条目顶部的结构:

1. **两行粗体标题**(总共 10-14 个词)。应该落地如判决,而不是营销。听起来像今天发布并且关心它是否有效的人。
2. **引言段落**(3-5 句)。发布了什么,对用户有什么变化。具体、具体,没有 AI 词汇,没有 em 破折号,没有炒作。
3. **"重要的数字"部分**,其中:
   - 一段简短的设置段落命名数字的来源(真实的生产部署或可重现的基准,命名要运行的文件/命令)。
   - 3-6 个关键指标的表,带有 BEFORE / AFTER / Δ 列。
   - 如果相关,则为每个类别的细分提供第二个可选表。
   - 1-2 句话用具体的用户术语解释最引人注目的数字。
4. **"这对[受众]意味着什么"结尾段落**(2-4 句)将指标与实际的工作流转变联系起来。以该做什么结束。

发布摘要的声音规则:
- 没有 em 破折号(使用逗号、句号、"...")。
- 没有 AI 词汇(delve、robust、comprehensive、nuanced、fundamental 等)或禁止的短语("here's the kicker"、"the bottom line" 等)。
- 真实的数字、真实的文件名、真实的命令。不是"快",而是"约 30 秒内 30K 页面"。
- 短段落,将单句拳头与 2-3 句段落混合。
- 连接到用户结果:"智能体少读约 3 倍"胜过"提高了精度"。
- 直接谈论质量。"设计良好"或"这是一团糟。"不要绕弯子。

来源材料:
- 上一条 CHANGELOG 条目作为先前上下文。
- 基准文件或 `/retro` 输出作为标题数字。
- 最近的提交(`git log <prev-version>..HEAD --oneline`)了解发布的内容。
- 不要编造数字。如果指标不在基准或生产数据中,请不要包括它。被问及时说"尚未测量"。

目标长度:约 250-350 字的摘要。应呈现为一个视口。

### 项目化更改(在发布摘要下方)

写 `### Itemized changes` 并继续详细的子部分(添加、更改、修复、For contributors)。与上面的面向用户的声音指南相同的规则,加上:

- **始终归功社区贡献。** 当条目包括来自社区 PR 的工作时,请使用 `Contributed by @username` 命名贡献者。贡献者做了真正的工作。每次都要公开感谢他们,没有例外。
